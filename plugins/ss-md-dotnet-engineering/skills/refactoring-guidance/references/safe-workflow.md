## Safe refactoring workflow

1. **Choose a concrete improvement.** Identify e.g. the rule that should have one owner, the computation whose intent is hidden, or the dependency obstructing the requested change. Select a transformation for that problem rather than selecting a pattern and looking for places to apply it.
2. **Protect the affected behavior.** Identify inputs, outputs, state changes, and callers that the transformation touches. Establish focused passing checks and a recoverable, known-good point before restructuring. Use the testing section to close gaps, not to rebuild the whole test suite.
3. **Transform one boundary at a time.** When moving only part of a method, extract that computation first; keep the old route working until its callers have migrated. Use symbol-aware refactoring tools where available, then inspect references the tools may miss, such as configuration names and framework registrations.
4. **Verify before stacking changes.** Run the relevant tests and build/type checks after each independently meaningful transformation. If a failure cannot be traced to the last step, return only your unverified edits to the last known-good point and replay them in smaller steps.
5. **Stop at a useful stable point.** Keep a tested extraction or move even if a larger hierarchy cleanup remains unfinished. Do not force the next step when it requires unexplained semantic changes. Run broader checks once the local sequence is stable, especially when shared code or runtime wiring changed. Reassess the original structural problem; passing tests alone do not prove the design improved. If further authorized work is needed to address it, continue in verified steps. If blocked or outside scope, identify what remains rather than present a partial migration as complete.

Inlining and re-extracting can deliberately repair poor method boundaries. Repeatedly switching between the same boundaries without improving naming, dependencies, or state flow signals a mistaken diagnosis, not progress.
